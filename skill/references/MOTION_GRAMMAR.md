# Motion Grammar

The canonical reference for `src/motion-grammar.js`. Everything in this document
is derived from that module, and the tables were generated by reading it — when
the grammar changes, regenerate them rather than trusting this prose.

```bash
node src/cli.js mechanisms          # the grammar, grouped by tier
node src/cli.js mechanisms --json   # the same data, for tooling
```

---

## 1. What a mechanism is

A **mechanism** is the smallest named unit of ASCII motion: one physical event
that a clip can perform, described as *material → action → emitted form*.

```js
{
  id: 'implosion',
  name: 'Implosion',
  tier: 'canonical',
  material: 'a dense orbiting mass collapsing inward',
  action: 'the mass is sucked into a focal glyph; density spikes to a point, then releases as a wave',
  emits: 'void',
  chainsTo: ['shockwave', 'cursor-vortex', 'giant-word'],
}
```

| Field | Meaning | Why it exists |
| --- | --- | --- |
| `id` | stable kebab-case key used by `planChain`, `allow`, `block` and the reviewer | identity that survives renaming |
| `name` | human label used in prompts and reviews | the audience-facing name of the event |
| `tier` | `canonical` \| `strong` \| `support` \| `reject` | how much structural weight the mechanism carries |
| `material` | what the audience sees moving | a mechanism must be made of something |
| `action` | what physically happens, as a cause | the sentence that becomes a prompt beat |
| `emits` | the **form** left behind | the key the next transition is looked up under |
| `chainsTo` | mechanism ids that inherit this motion well | a hand-authored hint, weaker than `emits` |

Two distinctions matter more than anything else on this page:

- **A mechanism is not a look.** It is a transformation. "Neon skyline" is a
  look; "a built environment is lost in stages, edges first, then surfaces, then
  the ground" is a mechanism.
- **`action` is written as a cause, not an adjective.** Every `action` string in
  the grammar can be dropped into a prompt beat verbatim, because each one names
  a physical event rather than a quality. `composePrompt` does exactly that.

There are **21 mechanisms**: 7 canonical, 7 strong, 2 support, 5 reject.

Two mechanisms declare no successors and no other mechanism chains into them:
`structural-decay` and `mask` (and `contour-migration` is likewise unreachable
from `FORM_SUCCESSORS`). They are still legal as an **opening** beat — the first
beat of a chain is chosen freely from the pool — and they are legal as a
hand-authored middle beat whenever the previous form admits them. They are
never chosen as a *successor* by the planner, which is why an automatically
planned chain rarely shows them.

Each mechanism also owns the sentence it leaves unresolved. `planChain` copies

## 3. The four tiers

The tier is a statement about **structural weight**, not about quality.

| tier | count | members | what it means | how the planner treats it |
| --- | --- | --- | --- | --- |
| **canonical** | 7 | `assemble`, `density-dissolve`, `structural-decay`, `letter-fragmentation`, `implosion`, `shockwave`, `cursor-vortex` | a load-bearing transformation: the film would not exist without events like these. They are the ones that make a clip read as motion rather than as a slideshow. | preferred first when candidates tie |
| **strong** | 7 | `boot-signal`, `contour-migration`, `tunnel`, `type-wall`, `glyph-sphere`, `giant-word`, `spatial-fold` | a high-impact event that carries a beat on its own: a camera punch-through, a scale inversion, a fold | preferred second |
| **support** | 2 | `field`, `mask` | material that carries motion handed to it. It never *causes* a transformation; it makes the previous one visible | used last, and as the renderer's fallback scene |
| **reject** | 5 | `reject-hud`, `reject-city`, `reject-glitch`, `reject-particles`, `reject-smoke` | a named failure mode | excluded from planning; present so it can be **named** |

Tier does not enter the prompt. A prompt that says "canonical implosion" has
wasted a word; a prompt that says "the mass is sucked into a focal glyph" has
spent it correctly.

### Why `reject` mechanisms are kept in the grammar

It is tempting to delete the failures. Keeping them buys four concrete things:

1. **`review()` can name the failure.** The `no-cliche` check iterates
   `MECHANISMS` filtered to `tier === 'reject'`, strips the `reject-` prefix, and
   searches the positive half of the prompt for `hud`, `city`, `glitch`,
   `particles` and `smoke`. Without the reject entries there is no vocabulary
   for the diagnosis — only a vague sense that the prompt feels cheap.
2. **`ruleLine()` can ban them by name.** `composePrompt` merges every cliché
   the brief triggered, plus a fixed default set, into the `RULE:` line. The
   RULE line is allowed to say "cyberpunk city" precisely because the *positive*
   prompt never does.
3. **They make the negative prompt a closed set.** `reject-*` is exactly the
   list of things this visual language refuses, so the ban is finite and
   reviewable instead of an infinite list of adjectives.
4. **They are terminal.** Each reject has `chainsTo: []` and `emits: 'cliche'`.
   `FORM_SUCCESSORS.cliche` contains exactly one mechanism, `boot-signal`: there
   is one way back into the grammar from a cliché, and it is to start over from
   a single mark. A cliché is not a bridge.

## 4. Forms and `FORM_SUCCESSORS`

A **form** is what a mechanism leaves behind. It is the currency of transition
legality: `planChain` looks up `FORM_SUCCESSORS[previousForm]` and picks from
that list. Adjacent mechanisms in a chain never need to be adjacent in the table
below — what has to match is the *form*.

| previous form | legal successors (tier, what they emit) |
| --- | --- |
| `void` | **boot-signal** (strong, emits letterform)<br>**assemble** (canonical, emits solid-form)<br>**cursor-vortex** (canonical, emits void)<br>**tunnel** (strong, emits space) |
| `field` | **assemble** (canonical, emits solid-form)<br>**density-dissolve** (canonical, emits field)<br>**type-wall** (strong, emits fragments)<br>**glyph-sphere** (strong, emits solid-form) |
| `particles` | **assemble** (canonical, emits solid-form)<br>**glyph-sphere** (strong, emits solid-form)<br>**field** (support, emits field) |
| `fragments` | **shockwave** (canonical, emits space)<br>**implosion** (canonical, emits void)<br>**cursor-vortex** (canonical, emits void)<br>**letter-fragmentation** (canonical, emits fragments) |
| `letterform` | **giant-word** (strong, emits letterform)<br>**letter-fragmentation** (canonical, emits fragments)<br>**mask** (support, emits letterform)<br>**spatial-fold** (strong, emits space) |
| `solid-form` | **density-dissolve** (canonical, emits field)<br>**contour-migration** (strong, emits solid-form)<br>**implosion** (canonical, emits void)<br>**type-wall** (strong, emits fragments) |
| `geometry` | **spatial-fold** (strong, emits space)<br>**glyph-sphere** (strong, emits solid-form)<br>**tunnel** (strong, emits space) |
| `space` | **type-wall** (strong, emits fragments)<br>**tunnel** (strong, emits space)<br>**spatial-fold** (strong, emits space)<br>**glyph-sphere** (strong, emits solid-form) |
| `cliche` | **boot-signal** (strong, emits letterform) |

`geometry` and `particles` are **orphan forms**: they are declared as keys with
legal successors, but no mechanism in the current table emits them (every
emitter produces `letterform`, `solid-form`, `field`, `fragments`, `space`,
`void` or `cliche`). They are the extension points for a future mechanism that
builds geometry or emits a particle state; `FORM_SUCCESSORS.geometry` exists so
that such a mechanism has somewhere legal to go the day it is added.

`review()` accepts a transition when **either** rule passes:

```js
const declared = prev.chainsTo.includes(cur.id);
const byForm   = (FORM_SUCCESSORS[prev.emits] ?? []).includes(cur.id);
if (!declared && !byForm) illegal.push(`${prev.id} → ${cur.id}`);
```

So the two tables are complementary. `chainsTo` is the director's opinion ("this
inherits well"); `FORM_SUCCESSORS` is the physical fact ("this form admits
this"). A planner uses the form table; a reviewer accepts either.

## 5. Camera grammar

The camera is graphic, never handheld. Eight moves exist:

| move id | when it is used |
| --- | --- |
| `forward-punch-through` | the default entry vector, and the exit of any mechanism that is not a drain |
| `rapid-scale-dive` | implosion-like compression toward a focal glyph |
| `orbital-lock` | a body orbiting a subject without a cut (glyph spheres, folds) |
| `spatial-fold-180` | a plane turning through itself |
| `planar-to-volume` | a flat field revealed as a volume |
| `sudden-freeze` | a hard arrival and hold, reserved for a deliberate stop |
| `tunnel-travel` | continuous travel down +z through rings |
| `backward-suction` | the drain: the frame is pulled backward into a small mark |

`CONTINUABLE_CAMERA` names the moves whose outgoing vector can be inherited
without a cut: `forward-punch-through`, `rapid-scale-dive`, `tunnel-travel`,
`orbital-lock`. A freeze and a fold are *arrivals*: they consume their own
vector, so a continuation that claims to keep them is not being honest about the
seam.

`planChain` sets an exit camera from the mechanism it picked:

```js
camera: pick.id === 'cursor-vortex' ? 'backward-suction' : 'forward-punch-through',
```

which is why a chain built by the planner always seams cleanly with `inherit()`.

## 6. The continuity contract

A clip is not allowed to end; it is allowed to **hand over**. The state that is
handed over is a `MotionState`:

| field | type | meaning |
| --- | --- | --- |
| `form` | string | what object/form exists at the cut point |
| `camera` | camera move id | the outgoing camera vector |
| `velocity` | number | signed apparent speed, roughly −3…3 |
| `rotation` | number | dominant rotation in turns/second |
| `scaleTrend` | +1 \| 0 \| −1 | growing, static, shrinking |
| `densityTrend` | +1 \| 0 \| −1 | densifying, static, dissolving |
| `unresolved` | string | the action the clip ends in the middle of |
| `palette` | palette name | the material identity |
| `ramp` | ramp name | the dominant charset |

Three functions own the contract:

```js
entryState(over)        // a legal way to open a clip
exitState(over)         // a legal way to close one
inherit(prevExit, opts) // prevExit BECOMES the next entryState
checkSeam(prevExit, nextEntry, opts) // returns violations; [] means the seam holds
```

### A worked example

Predecessor — a tunnel clip that ends mid-travel:

```js
const prevExit = exitState({
  form: 'space',
  camera: 'forward-punch-through',
  velocity: 1.2,
  rotation: 0,
  scaleTrend: -1,
  densityTrend: 1,
  palette: 'brutalist-digital',
  ramp: 'brutalist',
  unresolved: 'the camera is still inside the tunnel with speed left over',
});
```

Hand over:

```js
const entry = inherit(prevExit);            // speedUp defaults to 1.1
// {
//   form: 'space',                          // carried: the next clip opens inside the volume
//   camera: 'forward-punch-through',        // carried: the vector is not re-established
//   velocity: 1.32,                         // 1.2 × 1.1 — the sequel is faster, not restarted
//   rotation: 0,
//   scaleTrend: -1,
//   densityTrend: 1,
//   palette: 'brutalist-digital',           // carried
//   ramp: 'brutalist',                      // carried
//   unresolved: 'the camera is still inside the tunnel with speed left over',
// }
```

`inherit()` leaves `unresolved` populated on purpose: the sequel needs to know
what it is closing. `planContinuation` then states it in the prompt
(`Begin exactly as the previous clip's unresolved space completes its exit
motion.`) and the sequel's own chain opens a *new* unresolved action.

Verify:

```js
checkSeam(prevExit, entry, { requireCamera: true, requirePalette: true });
// []
```

### What `checkSeam` reports when the contract breaks

`checkSeam` is deliberately lenient by default. Camera, palette and charset are
only compared when the caller passes `requireCamera: true` / `requirePalette:
true`, because two independently constructed states may legitimately differ —
only a *declared* continuation promises material continuity. Velocity is always
checked, because a velocity break reads as a reset in any cut.

| break | how to trigger it | violation returned |
| --- | --- | --- |
| camera reset | `{ ...inherit(prevExit), camera: 'orbital-lock' }` with `requireCamera: true` | `camera vector resets: predecessor exits on "forward-punch-through" but the continuation enters on "orbital-lock"` |
| velocity dropped | `{ ...inherit(prevExit), velocity: 0 }` | `apparent velocity is dropped to zero, which reads as a hard reset` |
| velocity reversed | `{ ...inherit(prevExit), velocity: -1.2 }` | `apparent velocity reverses direction across the seam` |
| palette swapped | `{ ...inherit(prevExit), palette: 'phosphor' }` with `requirePalette: true` | `palette changes across the seam ("brutalist-digital" → "phosphor"), which breaks material continuity` |
| charset swapped | `{ ...inherit(prevExit), ramp: 'minimal' }` with `requirePalette: true` | `dominant charset changes across the seam ("brutalist" → "minimal")` |

Run it from the CLI:

```bash
# produce an exit state from a plan
node src/cli.js plan "<brief>" --json | node -e \
  "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.stringify(JSON.parse(s).chain.at(-1).exit)))" > exit.json

# plan the sequel; the seam verdict is printed before the gate
node src/cli.js continue exit.json "part two: <what happens next>"
# SEAM: holds — camera, velocity, palette and charset all inherit
```

If the seam does not hold, change the state, never the wording. A seam
violation means the two clips do not physically connect, and no adjective in the
prompt can repair a discontinuity.

## 7. Planning a chain from the grammar

`planChain(opts)` is the only planner. It is fully deterministic and never calls
the RNG; the same options always return the same chain.

| option | default | effect |
| --- | --- | --- |
| `count` | `6` | how many beats to attempt |
| `startForm` | `'void'` | the form the film opens from |
| `duration` | `15` | total seconds; each beat is `duration / count` long |
| `seed` | — | accepted for API symmetry; the planner is seed-independent by construction |
| `allow` | — | restrict the pool to these mechanism ids |
| `block` | — | remove these mechanism ids from the pool |

The algorithm, in order:

1. Build the pool: every mechanism whose tier is not `reject`, minus `block`,
   intersected with `allow` when one is given.
2. **The first beat is chosen freely from the pool.** A caller who writes
   `allow: ['implosion']` is stating what the film is about; filtering that by
   the `void` successor list would plan nothing at all.
3. Every later beat comes from `FORM_SUCCESSORS[form]`, narrowed to mechanisms
   the predecessor declares in `chainsTo` when any exist.
4. **A chain must not repeat a mechanism.** When nothing new legally follows, the
   planner shortens the chain (`break`) rather than looping back. This is why
   `planChain({ count: 40 })` returns 9 links: 9 is the length of the longest
   distinct legal path the current grammar admits, and a repeat would read as a
   stall.
5. Ties are broken by "how many onward options does this mechanism's emitted
   form have", then by tier (`canonical` before `strong` before `support`), so
   the chain does not paint itself into a corner in its last beats.

Each link is `{ mechanism, beat, from, to, exit, description }`, where `exit` is
a full `MotionState` whose `form` is the mechanism's `emits` and whose
`unresolved` is the mechanism's own sentence from §2.

## 8. Adding a new mechanism

Three places must change, and one of them is not in this module.

1. **`src/motion-grammar.js` — the `MECHANISMS` array.** Add the object with all
   seven fields. Choose `emits` from a form that already exists in
   `FORM_SUCCESSORS`, or add a new form (see step 2). Also add the mechanism's
   `unresolved` sentence to the private `UNRESOLVED` table at the bottom of the
   file; without it, `unresolvedFor()` falls back to
   `'the motion is still resolving when the clip ends'`, which is true but says
   nothing.
2. **`src/motion-grammar.js` — `FORM_SUCCESSORS`.** Make the new mechanism
   reachable by adding its `id` to the successor list of every form that should
   be able to lead into it, and make it a good citizen by listing what its own
   `emits` form admits. If it emits a brand new form, add that key too — and add
   the new form to at least one predecessor's list, or nothing will ever reach
   it.
3. **`src/renderer.js` — `MECHANISM_SCENES` and `cameraFor`.** Add a scene
   builder under the mechanism's id (a function `(seed) => Primitive[]` built
   from `PRIMITIVE_BUILDERS`: `pointCloud`, `rings`, `sphere`, `walls`, `slab`,
   `vortex`, `plane`, driven by the motion verbs `converge`, `expand`, `travel`,
   `spin`, `fold`, `dissolve`, `assemble`, `pulse`, `vortex`), and add a camera
   case in `cameraFor(mechanismId, u, duration)`. A mechanism with no scene falls
   back to `MECHANISM_SCENES.field`, so a preview will still render — but it will
   render the wrong idea, which is worse than rendering nothing.

Then prove it:

```bash
node src/cli.js mechanisms | grep -A2 <new-id>     # it is in the grammar
node src/cli.js preview "<brief mentioning it>"    # it renders
node test/engine.test.js                           # it is legal and reachable
```

The test suite will fail if the new id breaks the invariants in §4: it checks
that every `chainsTo` target resolves, that every `FORM_SUCCESSORS` entry
resolves and is non-rejected, that no planned chain repeats a mechanism, and
that every non-rejected mechanism renders a non-empty frame.
